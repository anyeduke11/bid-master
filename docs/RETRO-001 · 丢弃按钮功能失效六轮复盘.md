## 2. Why —— 根因分析

### 2.1 根因链（5-Why）

```
为什么点击丢弃无反应？
← 浏览器里丢弃事件的监听器从未被注册（不是注册了没触发）

为什么监听器没注册？
← 页面主脚本在顶层执行时于 1107 行抛出 TypeError 后终止，
   其后的一切注册（含丢弃）全部未执行

为什么 1107 行抛 TypeError？
← $("auto-refresh") 返回 null（HTML 中不存在该 id），null.addEventListener 崩

为什么元素不存在还有绑定代码？
← kanban v2 前端重构/cron 面板迭代时，按钮 id 改动或移除，
  绑定行未同步——死绑定随批量提交入库，无任何检查拦截

为什么死绑定能潜伏且潜伏期间无告警？
← ① 前端零运行时错误上报（js_error 无人知）
  ② make gate 只有静态检查（语法/JSON/契约），零前端运行时/E2E 覆盖
  ③ 用户页面长期不刷新（epoch 轮询让旧页面"看起来活着"），
     旧页面跑的是崩溃行引入之前的代码——崩溃只影响"新加载的页面"，
     而新加载的页面在修复部署前从未被打开过
```

### 2.2 双故障交汇（为什么这么难查）

```
用户浏览器页面（长驻，09-1x 加载）
  └─ 跑的是崩溃行引入之前的 JS → discard = confirm() 版
       └─ confirm 被内嵌浏览器静默吞掉 → "点不动"        【故障 A：交互层】

服务端静态文件（昨日批量提交后）
  └─ 已含死绑定行 → 任何新加载的页面在 1107 行崩死
       └─ 全页交互瘫痪（比 A 更严重，但没人新开页面所以未暴露）【故障 B：脚本层】

R1~R4 的修复全部写入静态文件 = 落在故障 B 的死区里
用户点不动 = 故障 A（旧页面）+ 故障 B（刷新也无用）叠加
直到 R5 信标上线，两个世界才被区分开来
```

### 2.3 为什么前四轮都"修了但没用"（LLM 协作视角，详见 §5）

每轮的缺陷诊断**都是真的**（confirm 吞噬/过滤缺失/状态脆弱均经代码证实），但存在系统性盲区：
1. **零客户端可观测性**——所有验证都止步于服务端（API 实测、DB 查询、代码审查），"用户浏览器里实际发生了什么"全程黑盒
2. **部署模型假设错误**——默认"重启服务=用户看到新版"，未建模"长驻页面"的客户端生命周期
3. **修复送达无法验证**——没有版本指纹机制，"用户跑的哪版代码"这个问题直到 R4 才被提出、R5 才有手段回答

## 4. How —— 修复与防御机制（已落地）

### 4.1 交互层
- `confirmBtn()` 两段式确认：首点进入待确认态（虚线描边+脉冲动画），同键再点执行，8s 超时自动还原——原生 confirm 的完整替代
- 丢弃专项：`LEADS_ARMED` Set（按 lead pk、String 归一）驱动渲染 + **整卡变淡**视觉反馈——重渲染免疫

### 4.2 数据层
- `load_leads` 默认排除 `lifecycle='discarded'`：确认丢弃=从视图删除，DB 行保留审计

### 4.3 脚本层（根因）
- `on(id,ev,fn)` 安全绑定助手：id 缺失 → `bind_miss` 信标 + console.warn + 跳过——**单点缺陷不再可能瘫痪整页**
- 死绑定行已替换（auto-refresh 在 kanban v2 重构后不存在，安全跳过）

### 4.4 可观测层（本轮最大资产）
- **信标系统**：`POST /api/v1/debug/beacon` → `log/client-beacon.jsonl`（限长+去控制字符防注入）；客户端插桩 `boot` / `js_error` / `unhandledrejection` / 关键点击全流
- **版本握手**：epoch 端点附 index.html 内容指纹（mtime 缓存）；页面启动自算哈希、5s 比对、不一致自动 reload——三方一致已实测（服务端/磁盘/页面 `b424643bd` 级别吻合）
- **动态 build 标识**：顶栏实时显示当前构建指纹

### 4.5 验证矩阵（本轮新增的 harness 能力）

| 验证手段 | 覆盖 | 首次投入使用的轮次 |
|---|---|---|
| 命令审计表（DB） | 服务端是否收到请求 | R4 |
| API 直测（curl/bid CLI） | 服务端逻辑正确性 | R1 |
| 静态绑定审计脚本（37 绑定 vs 112 静态 id） | 顶层注册完整性 | R6 |
| vm.Script 编译检查 | JS 语法 | R3 |
| **信标（客户端→服务端日志）** | **用户浏览器内实际发生的一切** | **R5（转折点）** |
| **playwright 真实浏览器 E2E** | **加载零崩溃 + 渲染 + 交互全旅程** | **R6（终局验证）** |
| 版本握手三方哈希比对 | 部署送达一致性 | R4/R6 |

## 5. Harness 工程复盘

### 5.1 既有 harness 的结构性盲区

bid-master 的质量基建在服务端相当完善（gate 8 子目标、26 条门禁安全带、36 项 API 契约快照、52 项 quality-test、reconcile 登记制审计），但存在一条**完整的覆盖断层**：

```
语法 ✓ → 服务端逻辑 ✓✓✓ → 契约 ✓✓ → 【前端运行时 ✗】【浏览器交互 ✗✗】【部署送达 ✗】
```

丢弃按钮恰好落在断层正中央：服务端命令管线被四层测试保护，而它的前端触发器**零保护**。断层不是疏忽——kanban v2 前端（约 100KB 单文件 SPA）从未被纳入任何测试视野，gate 里甚至没有 JS 语法检查。

### 5.2 本轮沉淀的 harness 资产（建议制度化）

| 资产 | 作用 | 制度化建议 |
|---|---|---|
| 信标系统（常驻） | 客户端错误/交互流可观测 | 保留常驻；`bind_miss`/`js_error` 出现即看板告警（候选） |
| playwright E2E 脚本 | 真实浏览器全旅程断言 | 纳入 `make gate-e2e`（可选目标）：加载零 pageerror + 关键按钮存在 + 冒烟交互 |
| 顶层绑定静态审计 | 绑定 id 与静态 HTML 比对 | 纳入 gate（防死绑定复发）；顶层注册一律走 `on()` |
| 版本握手 | 部署送达保障 | 已常驻；推广为前端标准模式 |
| vm 编译检查 | JS 语法门 | 已引入（提交时手工）；候选纳入 gate |

### 5.3 Harness 领域的核心教训

> **"验证了语法 ≠ 验证了运行时；验证了服务端 ≠ 验证了客户端；AI 会话里能跑 ≠ 用户浏览器能跑。"**
> 三条不等式的任何一条不补齐，对应层的问题就会以"时好时坏/莫名失效"的形态出现，且排查成本指数放大（本轮 6 轮 vs 信标后 1 轮）。

## 6. LLM 协作领域复盘（AI 调试行为分析）

### 6.1 行为模式：假设驱动 vs 证据驱动

前四轮的工作模式是**假设驱动**：每轮从代码审查出发构造"最可能的缺陷假设"→ 证实假设为真 → 修复 → 请求复测。四轮的假设全部被证实为真实缺陷——但根因不在其中。LLM 在缺乏客户端证据时，系统性地偏向"我能验证的层"（服务端/代码文本），而真实根因在"我不可见的层"（用户浏览器运行时）。

**R5 的信标部署是模式转换点**：从"我猜→我修→你试"转为"你点→日志说→我修"。R6 一轮定位。度量对比：假设驱动 4 轮 0 根因；证据驱动 1 轮 1 根因。

**制度建议**：对不可观测组件的缺陷，第一动作应是**先部署观测（信标/日志/复现 harness），再动手修复**——即使第一轮就"碰巧"修中，harness 也能证明它。

### 6.2 确认偏误实例

R3 中"龙潭校区条目已是 discarded 状态"被引用为"两段式确认生效"的证据——事后审计表显示该条的丢弃发生在 **09-13**（早期会话测试），与本轮用户操作无关。单一历史数据点被用来支撑当前假设，是典型的确认偏误。**教训：引用状态证据时必须核对时间戳与操作来源（agent_id/审计表）。**

### 6.3 LLM 输出验证（WebFetch 幻觉案例，DEV-0063）

追链接时 WebFetch 模型"补全"了不存在的 URL 目录（`/cgxm/` vs 实际 `/cgxmjg/`），直接采信会写入 404 死链。当日流程（构造 URL 先验证再采信）拦下了它。**LLM 生成的引用/链接/代码路径，一律视为待验证假设**——本轮丢弃事件的"先验证再 patch"纪律与信标建设同源。

### 6.4 修复引入新缺陷（无验证的修复=新 bug）

R3 的 Set 方案引入 `LEADS_ARMED.has(l.id)`（数字）与 `dataset.discard`（字符串）的类型不匹配——armed 视觉态**从未正确显示过**，直到 R4 才发现并修正。根因仍是缺 E2E：任何一次真实浏览器冒烟都能当场暴露。**"修复必须与验证同批交付"应成为 AI 协作硬纪律**（本轮 R6 的 playwright 断言即为该纪律的执行样板）。

### 6.5 用户语言的信息含量

- "点击丢弃，然后确认丢弃，确认则删除"——用户在描述**期望交互**，同时暗示"确认了但没删"（当时真因=列表过滤缺失，已修）
- "多次测试依旧存在问题"——**统计信号**："多次+依旧"指向恒定性失败而非竞态（与 R3 的竞态假设部分矛盾），应更早追问"是每次都不动，还是偶尔成功"
- **制度建议**：AI 收到模糊缺陷报告时，先做症状分类三问（每次都失败？有无任何反馈？其他按钮正常吗？）——三问答案能砍掉一半假设空间。本轮若先问，R2 即可导向监听器注册层。

### 6.6 正面沉淀（可复制的 AI 协作模式）

- **证据先行**：R4 的命令审计表查询（零浏览器 POST）是全程最有价值单条证据
- **真浏览器复现**：R6 用 playwright 以用户同视角复现，终结所有理论分歧——"与其推断用户环境，不如把用户环境搬进测试"
- **修根因前先修可观测性**：R5 信标看似"绕路"，实为最短路径

## 10. 结语

本事件表面是"一个按钮没反应"，实质是**三类问题在同一入口叠加**：产品缺陷（内嵌浏览器吞对话框）、工程断层（前端零测试覆盖 + 一行死绑定）、协作盲区（AI 修的送不到用户手里）。六轮过程中，价值最高的动作不是任何一次修复，而是 R5 的**信标部署**——它把"不可见"变成"可见"，此后一切迎刃而解。

对 ZCode 产品的启示浓缩为一句话：**内嵌浏览器要成为合格的开发/使用界面，对话框语义、错误可见性、陈旧性感知三件事必须补齐**——这正是 §7 清单的全部内容。
