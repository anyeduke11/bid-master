# 一句话结论

`/Users/duke/bid-master` 不是普通的投标 CRM，也不是单纯的 AI 写标工具，而是在尝试构建一个**面向单个方案专家、本机运行、以投标生命周期为主线的工作操作系统与生产控制面**。

它当前最强的能力不是“自动写出一份标书”，而是把投标过程中的：

- 状态推进
- 证据引用
- AI 产物
- 风险检查
- 人工签核
- 归档复盘

逐步变成可追踪、可审计、可重建的系统行为。

但它目前也存在一个根本矛盾：

> 系统已经比较擅长控制“进入系统之后的流程”，但还没有完全解决“现实中的所有投标工作是否真的进入系统”。

因此，目前它更接近于：

> **治理能力较强的投标生产基础设施**

而还不是一个已经被真实业务充分验证的成熟“投标操作系统”。

------

# 一、这个项目究竟在解决什么问题

## 1. 表面问题：做标流程混乱

传统投标工作通常散落在：

- 招标网站
- 微信
- 邮件
- Word
- Excel
- 本地文件夹
- 临时脚本
- 人脑记忆
- 多个 AI 对话窗口

最终导致：

- 不知道当前标处于什么状态
- 不知道哪些任务已经完成
- 不知道某段承诺来自哪里
- 不知道 AI 产物是否经过审查
- 不知道哪些风险已经被确认
- 不知道上一次投标的经验有没有被真正复用

## 2. 项目真正试图解决的问题

项目的真正目标不是“生成更多文字”，而是建立一条受控链路：

```
发现线索
  ↓
是否值得投
  ↓
解构招标需求
  ↓
形成技术/商务方案
  ↓
审查证据与引用
  ↓
人工签核
  ↓
封标与开标
  ↓
结果复盘
  ↓
经验沉淀
```

也就是说，它在解决的是：

> 如何让一个高认知、高风险、强依赖经验的投标工作，变成可追踪的生产流程。

这个定位是合理的，而且比“AI 自动投标”更现实。

# 二、整体架构理解

## 1. 总体分层

当前项目大致可以分为六层：

```
┌──────────────────────────────┐
│        前端工作台             │
│ 今日必办 / 商机 / 管线 / 深潜 │
└──────────────┬───────────────┘
               │ HTTP / SSE
┌──────────────▼───────────────┐
│        API 与命令网关         │
│ Router / Command Engine       │
│ 幂等 / 审计 / Payload Hash     │
└──────────────┬───────────────┘
               │
┌──────────────▼───────────────┐
│        应用服务层             │
│ bids / leads / agents / runs  │
│ tickets / artifacts / events  │
└──────────────┬───────────────┘
               │
┌──────────────▼───────────────┐
│       确定性规则层            │
│ store / set_stage / verify    │
│ reconcile / desensitize       │
└──────────────┬───────────────┘
               │
┌──────────────▼───────────────┐
│       数据与产物层            │
│ truth.db / app.db / 文件 / KB │
└──────────────┬───────────────┘
               │
┌──────────────▼───────────────┐
│       Agent 与 Skill 层       │
│ scout / writer / locator      │
│ auditor / archivist           │
└──────────────────────────────┘
```

它不是微服务架构，而是一个：

> **本机单体服务 + 模块化应用层 + SQLite 数据层 + 文件生产区 + Agent 编排层**

这个选择对当前的单人、本机使用场景是合理的。项目没有过早引入网络服务、消息队列、云数据库和微服务，避免了大量基础设施复杂度。

------

## 2. 数据层：项目最重要的架构决策

项目的核心数据根目录是：

```
~/.bidmaster/
├── truth.db
├── app.db
├── bids/
├── leads/
├── memory/
├── runs/
├── queue/
├── agent_queue/
├── out/projection.db
└── log/
```

### `truth.db`

这是项目定义的真实层，主要承载：

- bid
- 阶段
- 阶段历史
- gate attempt
- artifact 登记
- ticket
- run
- lessons
- KB asset

它的目标是回答：

> 这个标当前到底处于什么状态？哪些状态变更是有效的？哪些产物已经被登记？

### `app.db`

它更像应用观察层和运营层，承载：

- leads
- 活动日志
- 命令执行记录
- 技能运行
- 运营事件

### 文件生产区

例如：

```
~/.bidmaster/bids/<bid_id>/
```

这里保存实际生产的标书材料、草稿、审查结果、证据文件等。

但文件本身不能直接成为系统事实。必须通过：

```
rules/store.py
```

登记为 artifact，才能被看板和生命周期系统消费。

### `projection.db`

这是冷恢复或投影数据库，理论上可以删除并重建，不应该成为事实源。

# 三、生命周期模型：从“修改状态”到“通过门禁推进”

项目的核心生命周期是：

```
S0 线索
S1 预审
S2 决策
S3 解构
S4 编制
S5 审查
S6 封标
S7 开标
S8 结果
S9 归档
```

关键设计在于：阶段不是自由字段，而是一个受规则控制的状态机。

主要规则位于：

```
/Users/duke/bid-master/rules/store.py
/Users/duke/bid-master/rules/set_stage.py
```

## 阶段推进的基本原则

- 只能逐级推进
- 不能随意跳跃
- 不能回退
- 门禁失败也要留下记录
- 某些阶段必须有人工签核
- 看板不应绕过状态推进脚本

例如：

### S2 → S3

要求：

- 完成预审
- 完成决策
- 记录 stage0
- 记录 lessons_applied

### S3 → S4

要求：

- 招标关键词与命中台账完成对账
- 对账率达到 100%

### S4 → S5

要求：

- 内容完整
- 规格单存在
- 素材匹配
- `verify_draft` 通过

### S5 → S6

要求：

- auditor 没有阻断问题
- locator 命中率达到要求
- `verify_audit` 通过
- 人工签核
- 使用 `--sign-off`

### S8 → S9

要求：

- 归档提案已确认
- 脱敏通过
- supersession 链完整

这套机制解决了投标系统最常见的一类问题：

> 看起来工作在推进，实际上没有证据证明工作完成了。

从工程角度看，这是项目目前最成熟的部分。

# 四、功能模块理解

## 1. 标讯发现与筛选

项目支持：

- 采集线索
- 线索同步
- 线索筛选
- 升级为 bid
- 丢弃线索

这里的目标不是简单地抓取更多信息，而是让线索进入后续决策链。

但需要注意：

> 采集能力是否真正覆盖现实中的全部线索，比筛选算法本身更关键。

如果线索仍然停留在微信、邮件或人工收藏夹中，那么系统的筛选再完善也只能处理一部分世界。

------

## 2. 投标管线

前端视图包括：

- 今日必办
- 采集
- 商机
- 管线
- 单标深潜
- 汇总
- 资产
- 系统

这说明项目不只是保存数据，而是在尝试提供一个日常工作控制台。

理想情况下，用户每天打开系统后应该能回答三个问题：

1. 今天必须做什么？
2. 哪个标的风险最高？
3. 哪些事情已经完成，哪些还缺证据？

这比传统 CRM 的“查看列表”更接近实际工作。

------

## 3. AI Agent 与 Skill

项目当前设计了多个角色：

- `main-agent`
- `bid-scout`
- `bid-writer`
- `bid-locator`
- `bid-auditor`
- `bid-archivist`

分工大致是：

| Agent         | 主要职责             |
| ------------- | -------------------- |
| main-agent    | 主语义链路、决策协调 |
| bid-scout     | 线索发现与初筛       |
| bid-writer    | 方案与标书内容生产   |
| bid-locator   | 引用定位、证据核查   |
| bid-auditor   | 审查与风险发现       |
| bid-archivist | 归档、复盘、知识沉淀 |

这里比较成熟的地方是：

> 项目没有把所有事情都交给 AI。

它明确区分：

- 语义判断：交给 Agent
- 确定性检查：交给脚本
- 状态推进：交给规则
- 最终批准：交给人

这是正确的责任划分。

# 五、第一性原理分析

第一性原理不是从“别人怎么做系统”出发，而是先问：

> 这个系统要成立，哪些事情必须永远成立？

我认为本项目至少有五个关键不变式。

------

## 不变式一：状态必须唯一且可重建

问题是：

> 同一个 bid，在任意时刻到底哪个状态是真实的？

项目采用 `truth.db` 作为事实源，用 `store.py` 作为主要写入口，这个方向是正确的。

但现在仍有多个状态表现形式：

- `truth.db`
- `app.db`
- `memory/bids.jsonl`
- `projection.db`
- 文件目录
- 旧 JSONL 数据面

因此当前状态是：

- **设计上：truth layer 已明确**
- **代码上：主要状态推进已集中**
- **架构上：仍然存在多个投影和兼容层**
- **风险上：写入边界还没有做到绝对单一**

如果未来删除 `projection.db` 后不能完整恢复业务视图，说明系统仍然有隐藏事实源。

------

## 不变式二：每个关键结论必须能回到证据

投标不是普通内容创作。

一句话“符合要求”，背后可能需要回答：

- 来源是哪一页？
- 来自招标文件还是经验？
- 是否有对应产品资料？
- 是事实、承诺还是推测？
- 谁审查过？
- 是否已经被 supersede？

项目通过以下机制支持证据链：

- artifact contract
- fingerprint
- locator
- `verify_draft`
- `verify_audit`
- stage history
- gate attempts
- run manifest
- ticket_id

这是一个很好的设计方向。

但需要警惕一个问题：

> 证据链存在，不等于证据链真的被高质量使用。

当前还需要用真实标书验证：

- 引用是否准确
- locator 是否能处理复杂 PDF
- 95% 的命中率是否真的具有业务意义
- 是否会为了通过门禁而制造形式引用
- 审计结果是否能有效减少返工

------

## 不变式三：敏感数据必须默认不进入 AI 边界

项目明确禁止以下内容进入 Prompt 或产物：

- 成本价
- 折扣
- 客户名单
- 证件号
- 证书编号

此外还引入了涉密标的壳模型：

- 只记录必要元数据
- 内容不进入系统
- 仍能参与生命周期追踪
- 看板仍然可以提醒工作

这是非常重要的现实主义设计。

否则会出现两个极端：

1. 为了安全，涉密项目完全脱离系统；
2. 为了方便，涉密内容进入 AI，造成重大风险。

但当前仍有一个边界问题：

> 系统主要依赖人工正确标记 classified，不能完全自动识别业务级敏感内容。

因此它目前是“有较强安全纪律的受信任本机工具”，不是自动安全分类系统。

------

## 不变式四：AI 不能通过自报完成度绕过检查

AI 最危险的行为之一是：

> 输出看起来完整，但没有真实完成。

项目通过以下方式限制这种情况：

- 产物必须登记
- 必须有 fingerprint
- 需要 run manifest
- 需要 ticket_id
- 需要自检结果
- locator 需要复算
- auditor 需要独立检查
- 关键阶段需要人工签核
- 产物必须是 `status=final`

这说明项目理解了一个重要事实：

> AI 的“我完成了”不是事实，只能算一种声明。

不过，仍需要更多真实样本判断门禁是否真的有效，还是仅仅提高了格式合规性。

------

## 不变式五：系统必须让人更快做正确的事

这是最终业务价值的判断标准。

系统不是为了拥有更多表、更多 Agent、更多 API，而是应该让用户：

- 少找文件
- 少重复录入
- 少忘记风险
- 少写错引用
- 少重复问同样的问题
- 更快发现高风险事项
- 更容易复用上一次经验

这个不变式目前只完成了一半。

产品界面和数据结构已经朝这个方向设计，但真实业务覆盖还不够充分，尤其是：

- 涉密工作
- 系统外沟通
- 临时 Word 文档
- 人工判断
- 外部文件路径
- 真实交付反馈

这些仍然可能绕过系统。

------

# 六、项目的主要优势

## 1. 状态机和门禁设计扎实

这是目前最有价值的部分。

项目已经把“状态推进”从：

```
某个人手动修改状态
```

变成：

```
满足条件
→ 规则检查
→ 记录尝试
→ 产生审计轨迹
→ 必要时人工签核
→ 阶段推进
```

这对投标业务非常重要。

------

## 2. AI 使用方式相对成熟

项目没有试图构建一个“完全自主投标 Agent”，而是将 AI 放进有边界的生产流程。

这种设计比以下做法可靠得多：

- 一个大 Prompt 生成全部内容
- 让 AI 自己判断是否合规
- 让 AI 自己决定是否完成
- 让 AI 自己写入所有状态
- 让 AI 自己批准自己的结果

------

## 3. 审计和可追溯能力较强

项目已经形成了比较完整的追溯链：

```
ticket
  → run
  → producer/model
  → artifact
  → fingerprint
  → locator
  → verify
  → gate attempt
  → stage history
```

这套链路的价值高于“单次生成质量”。

------

## 4. 对涉密场景有现实考虑

很多系统在面对涉密项目时只有两个选项：

- 全部纳入，安全风险很高
- 全部排除，业务覆盖率很低

本项目采用 classified shell，试图在两者之间取得平衡。

这并不能解决所有安全问题，但至少承认了真实世界：

> 如果系统不承载涉密项目的最低限度状态，它就无法反映真实工作全貌。

------

## 5. 工程质量控制已经成型

`make gate` 当前能够检查：

- Python 语法
- JSON
- Agent 契约
- 状态机安全带
- API 契约
- truth reconcile
- Skill 同步
- 仓库卫生

调查中门禁结果为：

- 安全带：36/36
- store/read_now：22/22
- digest 云脱敏：12/12
- API 契约：43/43
- agent 契约同步通过
- truth reconcile 通过

这说明它已经不是单纯的原型代码，而是具备一定持续回归能力的内部系统。

------

# 七、批判性分析：项目当前真正的问题

## 1. 最大问题：业务覆盖率低于治理复杂度

运行时数据表明，系统中当前只有少量真实 bid：

- `truth.db` 中约 1 个 real bid
- 约 61 个 artifact
- 约 8 个 ticket
- 约 27 个 run
- 约 13 个 lessons
- `app.db` 中约 21 条 leads

这说明：

> 系统的控制面已经很丰富，但真实业务流量还没有充分进入系统。

这是一个关键判断。

一个系统可以拥有：

- 很完整的状态机
- 很多 API
- 很多 Agent
- 很多检查
- 很多文档

但如果真实工作仍然发生在微信、Word、邮件和临时文件中，那么它最终只是：

> 一个精心设计的旁路工具，而不是业务的主系统。

------

## 2. 双库设计有合理性，但一致性代价高

`truth.db` 和 `app.db` 的分离本身不是错误。

问题在于，一个真实业务动作可能同时涉及：

- lead
- bid
- command execution
- event
- artifact
- stage history
- ticket

如果这些写入跨越多个数据库，那么就无法天然获得单事务原子性。

当前系统依赖：

- 约定
- reconcile
- 测试
- 补偿逻辑
- 运维纪律

这意味着系统在正常路径下可用，但故障路径仍可能复杂。

测试过程中出现过：

```
database is locked
```

虽然没有导致测试失败，但它是一个值得认真对待的信号。随着后台 watcher、SSE、命令执行、Agent 运行增加，SQLite 并发写入可能成为实际约束。

------

## 3. “唯一写口”还没有覆盖所有业务事实

项目的纪律要求是：

> 所有状态/登记写入只走 `rules/store.py`。

目前主要状态推进已经做到较好，但仍存在潜在旁路：

- `/Users/duke/bid-master/app/api/agents.py` 中某些路径直接修改 profile
- 某些服务直接写 app.db
- 线索 watcher 直接导入数据
- `rules/apply_archive.py` 同时处理文件、KB、lessons 和 ledger
- 部分旧规则脚本读取固定 `Path.home()`
- 某些文件写入后再登记，登记失败时需要补偿

因此需要区分两件事：

### 已经比较可信的

> bid 生命周期状态推进的唯一写口。

### 尚未完全成立的

> 整个系统所有业务事实的唯一写口。

后者如果不解决，未来很容易出现：

- 数据库说一套
- 文件说一套
- UI 投影说一套
- Agent 上下文又说一套

------

## 4. 复杂度可能已经超过当前业务规模

项目服务的用户是单人 Duke，月均真实投标量并不高，但当前系统已经包含：

- 十阶段状态机
- 双数据库
- 六类 Agent
- 多种 artifact contract
- 二十多个命令
- 四十多条 API 路由
- SSE
- watcher
- launchd/cron
- KB 生命周期
- 工单体系
- 多套历史文档和设计方案

复杂本身不一定错误，但必须持续问：

> 这个复杂度究竟减少了多少返工、错漏、合规风险和找文件时间？

如果不能量化，系统可能出现反效果：

> 用户需要花很多时间维护投标系统本身。

这是内部工具最危险的失败模式之一。

------

## 5. 文档体系存在漂移

当前仓库中存在多个时期的：

- PRD
- 架构审查
- 数据协议
- 设计文档
- backlog
- 复盘文档

已有迹象表明：

- README 仍有旧版本命令数量或语义
- `set_stage.py` 的部分文档字符串保留旧 JSONL 时代表述
- `docs/data-plane-protocol.md` 与最新 truth.db 设计存在历史叠层
- backlog 中有些事项已经完成或迁移，但仍未清理

对普通项目而言，文档漂移只是维护问题；对本项目而言，风险更高，因为：

> Agent、脚本和人都可能把文档当成运行协议。

建议未来把文档分成三类：

1. **当前有效协议**
2. **历史决策记录**
3. **废弃方案**

不要让三者处于同一语义层级。

# 九、建议的后续优先级

## P0：验证系统是否真的覆盖真实工作

先不要继续增加 Agent 或 API，做一次完整真实工作日演练。

建议所有真实项目都建立最小壳：

- real bid：可进入全部流程
- classified bid：只进入元数据和任务流程
- 外部工作：至少登记为 ticket 或 activity
- 临时产物：进入 artifact 索引
- 最终结果：回写 S8/S9

重点统计：

- 有多少真实标没有进入系统
- 有多少次需要重复录入
- 有多少次找不到最新状态
- 有多少门禁真正阻止了错误
- 有多少门禁只是增加操作负担
- 今日必办是否真的帮助决策
- 归档经验是否真的影响下一标

------

## P1：收敛数据和写入边界

重点不是重写架构，而是减少旁路。

建议：

1. 所有路径统一使用配置中心，不要混用固定 `Path.home()`。
2. 明确 `truth.db` 与 `app.db` 的权责边界。
3. 对跨库写入增加补偿记录和失败恢复。
4. 将直接写业务数据的 API 纳入 command gateway。
5. 明确 `projection.db` 的重建机制。
6. 清理历史 JSONL 兼容路径。
7. 针对 `database is locked` 做并发写入压力测试。

------

## P2：验证知识飞轮，而不是继续扩展知识结构

需要验证完整链路：

```
归档提案
  → 人工确认
  → lesson 入库
  → 下一标加载
  → 影响决策或内容
  → 复盘验证是否有效
```

真正有价值的不是“系统里有 13 条 lessons”，而是：

> 下一次投标是否因为某条 lesson 少犯了一个错误、少走了一条弯路。

# 十、暂时不建议优先做的事情

在真实业务闭环验证之前，不建议优先：

- 新增更多 Agent
- 引入消息队列
- 引入向量数据库
- 微服务化
- 做移动端
- 继续扩大 API 数量
- 大规模重写前端
- 继续堆积 PRD 和原型
- 为尚未验证的场景设计更复杂的自动化

原因很简单：

> 当前瓶颈不是生产能力不足，而是现实工作没有完全进入系统。

# 十一、最终判断

这个项目最值得肯定的地方，是它没有把投标理解成“写一篇文章”，而是理解成一个包含：

- 信息采集
- 资格判断
- 需求解构
- 方案生产
- 证据核验
- 风险控制
- 人工审批
- 结果复盘

的连续生产系统。

它最重要的技术成果，不是某个 Agent 或某个 UI 页面，而是建立了：

> **状态机 + 证据链 + 门禁 + 人工签核 + 可审计产物**

这一整套治理骨架。

但批判性地看，项目下一阶段不能继续只从“系统还能增加什么能力”出发，而应从以下问题出发：

> 现实中的投标工作，有多少真正进入了这套系统？
> 系统是否真的减少了错误、返工和认知负担？
> 如果没有 AI，这套流程是否仍然成立？
> 如果没有人工兜底，哪些地方会失效？
> 系统复杂度是否已经超过了它带来的收益？

目前最核心的结论是：

> **项目在工程上已经具备较强的治理骨架，在业务上仍处于真实闭环验证阶段。**
