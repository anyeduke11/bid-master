!现状诊断 · 6 个真问题
问题 1 · 流程只有 1/5,不是"招投标",是"投标中段"

13 节点模板(sales-bid → buy-rfp → ... → retro)全是"投标"环节。缺:标讯抓取 / 客户识别(可参与?) / 中标交付 / 项目归档。网络安全销售/售前的真实链路比这长 4 倍。

问题 2 · 数据是"测试",不是"业务"

6 客户是手工塞的(东莞/农发/银联/平安/国信),reset 一键全清。缺:真实抓取入口 / 数据归档 / 历史查询。现在只能在演示态。

问题 3 · 没有"手动",只有"自动"

每个流程节点只能点 playbook 跑,不能手动改状态。缺:手动状态切换按钮 + 自动剧本两条路。真实工作 70% 是手动判断,30% 才是自动化。

问题 4 · 无时间维度总结

没有周报/月报/季报/年报,每周/每月复盘要自己从日志里捞。缺:聚合视图(本周新增/本周推进/本周中标/本周流失 + 客户/行业/区域/产品多维分析)。

问题 5 · skill 过度依赖 AI,无脚本化

5 个 playbook 全是内联 lambda,没法独立测试,没法复用到其他项目。缺:脚本优先(python/bash) + AI 仅做语义层(标书摘要/客户画像)。

问题 6 · 日志未收敛,前后端不一致

前端 event-bar 展示 200 条但运行过程全展示太噪;后端只有 stderr print,没文件没结构。缺:分级(debug/info/warn/error) + 文件落盘 + 后端查询 API。

2扩展 2:手动 + 自动双通道

每个节点都有 2 个入口:⚡ 手动改状态(立即生效) / ▶ 跑剧本(按步骤自动)。

// 节点 click 后弹出:节点详情弹窗(已有,扩展) /* ┌─────────────────────────────────┐ │ quote · 报价 · plan 12-21 │ ├─────────────────────────────────┤ │ 状态: [progress ▼] │ ← 手动改 │ 阻塞: [ ] │ │ 截止: [ ] │ ├─────────────────────────────────┤ │ [⚡ 手动应用] [▶ 跑自动剧本] │ ← 双按钮 │ [取消] │ └─────────────────────────────────┘ */

手动:用户改 state,直接 PATCH /api/flow/node,立即生效,写 1 条日志

自动:跑 playbook(5+1+1=7 个),按 step 走,每 step 写 1 条日志

选择:默认走"手动"(业务主导),只在用户明确点"跑剧本"时才自动

3扩展 3:数据生命周期 + 归档
状态含义进入条件看板可见性
active 活跃(默认) 新建时 看板主视图
paused 暂停(等客户回信/等预算) 手动标记 + 暂停原因 看板折叠区(不占主屏)
closed 关闭(已结案) 中标交付完成 / 丢标确认 看板"近期关闭"区(7 天可见)
archived 归档(冷数据) closed + 30 天 / 手动归档 默认隐藏,搜索可见

自动归档规则(避免数据堆积):

  • closed 状态超过 30 天 → 自动 archived
  • active 状态超过 90 天无 last_sync → 自动 paused + 提醒
  • 手动归档按钮(批量)

归档数据不丢:JSON 落盘 ~/.bidboard/archive/YYYY-Q.jsonl,看板隐藏但搜索/统计/复盘全可用。

4扩展 4:时间维度总结 · 周/月/季/年

📅 周报

本周(周一-周日)聚合:

  • 新增商机 / 推进中 / 中标 / 丢标 / 暂停
  • 预计成交金额(加权)
  • P0 客户数(本周变化)
  • 阻塞解决平均时长
  • Top 3 风险客户

📅 月报

本月 + 客户/行业维度:

  • 月新增 / 月中标 / 月丢标
  • 客户分布(新增 vs 跟进 vs 沉默)
  • 行业分布(银行/政府/企业/其他)
  • 区域分布(华南/华北/华东)
  • 赢率 = 中标 / (中标+丢标)
  • Top 5 客户(按金额)

📅 季报

本季 + 趋势分析:

  • 季度汇总 + 同比/环比
  • 客户分级(大客户/中小/小微)占比
  • 产品/服务线分析
  • 竞争对手分析(从丢标原因聚合)
  • 预测(下季度)

📅 年报

本年 + 战略层:

  • 年度汇总 + 多年趋势
  • ROI(投入 vs 产出)
  • 战略客户清单 + 健康度
  • 产品组合分析
  • 团队产能(人均中标数/金额)
  • 下一年度规划建议

实现方式:每个 bid 加 created_at / updated_at / closed_at / archived_at 时间戳,服务侧按时间段聚合,前端 1 个"📅 总结"tab。

5扩展 5:skill 脚本化 + 日志收敛

5.1 playbook 改为调用外部脚本

现有 playbook 都是内联 lambda,改成 subprocess.run() 调用 scripts/ 目录下的独立脚本:

# bid-board/scripts/ ├── lead_capture.sh # L1 标讯抓取(curl + jq) ├── qualify_score.py # L2 AI 评分 ├── bid_dongguan.sh # L3 东莞剧本(纯 bash) ├── bid_nfh.sh # L3 农发剧本 ├── delivery_extract.py # L4 合同要素抽取 └── archive_close.py # L5 归档 # server.py 改为: PLAYBOOKS = [ {"id": "pb-collect", "script": "scripts/lead_capture.sh", "args": {"date": "today"}, "desc": "..."}, ... ] # 执行: subprocess.run(["./scripts/bid_dongguan.sh", code], capture_output=True, timeout=30)

好处:

  • 脚本可独立测试(./scripts/lead_capture.sh --date 2026-08-14)
  • 复用给其他系统(可直接 cron 跑)
  • 不依赖 LLM 启动,执行快
  • AI 只在需要时调(qualify_score.py 的语义部分)

5.2 日志分级 + 文件落盘 + 后端查询

# 日志结构 log_entry = { "ts": "2026-08-14 09:43:05.36", "level": "info", # debug / info / warn / error "module": "playbook", # playbook / api / system / script "code": "dgyhst2026", # 关联 bid "msg": "pb-dongguan step 2 完成", "payload": {...} } # 落盘 ~/.bidboard/ ├── log.jsonl # 全部日志(append-only) ├── bids.json # 当前活跃 ├── archive/2026-Q3.jsonl # 归档 └── stats.json # 缓存的统计 # 后端 API GET /api/logs?level=error&code=dgyhst2026&from=2026-08-01&to=2026-08-14 GET /api/logs?module=playbook&keyword=签字

前端:管理 tab 日志区只展示 warn + error 摘要,点"展开"才看全部 + 过滤。

后端:curl /api/logs 直接查询,可管道到 grep/jq。
