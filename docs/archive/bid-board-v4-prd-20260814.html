0第一性原理
系统唯一职责 = 经营事实源。不是"工具集合",不是"自动化平台",不是"AI Agent"。它只回答 4 个问题:
  1. 发现事实:外部 Agent 在什么时间、通过什么来源发现了什么?(可观察、可审计,但不可直接改变业务)
  2. 业务事实:平台认可的 Bid / Lead / Opportunity / Quotation / Contract / Delivery / Invoice / Payment 各是什么状态
  3. 业务决策:谁以什么理由推进了哪个状态(谁、什么时间、什么命令、什么参数、什么证据)
  4. 可追溯结果:任意一条数据可以回溯到 Agent / Skill / 外部运行 / 同步批次 / 证据 / 命令
推论:Agent 不能直接写库。报告不能成为事实唯一来源。推荐不能自动变客户/合同。所有业务更新必须是已注册命令,而不是任意 PATCH。

2数据模型 · 三层分区
🟦 外部观察层 (Collection · 可部分失败,可重复,可复核,不可直接改 LTC)

表: collection_run(批次,含时间/来源/状态) · collection_channel_run(单渠道) · sync_batch(同步批次,带 idempotency_key) · sync_item(单条,带 payload_hash,状态:applied/rejected/pending_review) · bid_evidence(证据,链接/截图/原文) · report_artifact(报告,只存摘要+引用,不存全文) · external_action_result(外部动作结果)

🟩 平台事实层 (Platform · 人工或命令确认的经营事实)

表: bid(规范采购事实) · customer(确认企业对象) · lead(业务资格,来源 collection 提升) · opportunity(销售机会) · quotation(报价) · contract(合同) · delivery(交付) · invoice(发票) · payment(回款) · ai_summary(只存引用 + 作者 + 时间,不当事实)

🟪 控制层 (Control · 安全与追溯)

表: agent_credential(token + scope) · agent_request_audit(请求审计:谁/何时/什么 IP) · command_execution(命令执行:commandId/params/状态/result) · domain_event(领域事件) · activity_log(活动日志) · data_quality_task(数据冲突复核任务) · lifecycle_state(lifecycle + created_at + updated_at + closed_at + archived_at)

5标准调用协议

5.1 HTTP 命令调用

POST /api/commands Headers: Content-Type: application/json Idempotency-Key: <uuid> ← 必须 Payload-Hash: <sha256> ← 必须 Authorization: Bearer <token> ← 生产模式 Body: { "commandId": "bid.update_stage", "params": { "code": "dgyhst2026", "stage": "封标", "reason": "评审通过", "evidence_refs": ["ev_001", "ev_002"] ← 可选,引用 collection 表 } } Response 200: { "ok": true, "commandId": "bid.update_stage", "executionId": "cmd_abc123", "result": {...}, ← 业务结果 "appliedAt": "2026-08-14 13:00:00" } Response 200(幂等重放): { 返原结果 } Response 409: { "err": "IDEMPOTENCY_PAYLOAD_MISMATCH" } ← 相同 idempotency_key 但 payload_hash 不同

5.2 CLI 接口

$ bid-board capabilities $ bid-board commands list # 列出所有已注册命令 $ bid-board run bid.update_stage --code dgyhst2026 --stage 封标 --reason 评审 $ bid-board status --execution cmd_abc123 # 查询命令执行状态 $ bid-board replay --execution cmd_failed_xyz # 管理员重放 $ bid-board export --entity opportunities --format json --out opps.json $ bid-board import --file leads.json --type collection # 导入外部 lead

5.3 幂等保证

# 相同 Agent + idempotency_key + payload_hash → 返原结果 # 相同 idempotency_key 但 payload_hash 不同 → 409 IDEMPOTENCY_PAYLOAD_MISMATCH # 不同 idempotency_key 视为新命令 # 命令状态机保证:bid.update_stage 在相同 (code, stage) 时返原结果
6事务化(审计失败不能返回成功)

所有命令执行必须在单 SQLite 事务中完成:

def execute_command(commandId, params, idempotency_key, payload_hash, agent_id): with sqlite3.connect(DB_PATH) as conn: conn.execute("BEGIN IMMEDIATE") # 串行化,避免并发写竞争 try: # 1. 幂等检查 existing = lookup_by_idempotency(conn, idempotency_key) if existing: if existing.payload_hash != payload_hash: return 409, "IDEMPOTENCY_PAYLOAD_MISMATCH" return 200, existing.result # 重放 # 2. 验证命令 + scope validate_command(commandId, params, agent_id) # 3. 业务写(在 domain 层) result = dispatch_to_domain(commandId, params, conn) # 4. 写 CommandExecution exec_id = insert_command_execution(conn, commandId, params, result, agent_id) # 5. 写 ActivityLog + DomainEvent insert_activity_log(conn, exec_id, agent_id) insert_domain_event(conn, commandId, exec_id) conn.execute("COMMIT") return 200, result except Exception as e: conn.execute("ROLLBACK") # 即使失败,也要写 failed CommandExecution(独立事务) log_failed_execution(commandId, params, str(e), agent_id) return 500, {"err": str(e)}

9批判性审查(对自己方案的反思)
问题 1 · 个人使用 vs 多用户:v0.3 是"多 Agent 多用户数据中台",bid-board 是"个人看板"。把整套协议照搬可能过度设计。
决策:核心原则(命令化/幂等/审计/LTC)借鉴,认证/scope/data_quality_task 推到 P2(可选)。
问题 2 · SQLite 够不够:v0.3 用 Prisma + SQLite 支持中型场景。当前 bid-board 单用户完全够,加事务 + 索引足够。
决策:不引入 Prisma/ORM,直接 sqlite3 stdlib,降低复杂度。事务用 `BEGIN IMMEDIATE` 保证串行。
问题 3 · 8 张新表是不是太多:collection_run/lead/opportunity/quotation/contract/delivery/invoice/payment 全分,小项目用 1 张 bids 就能装。
决策:先做 collection + bid + command_execution + activity_log 4 张核心表,其他表用 JSON 字段延后(等业务真有 LTC 流转时再分)。
问题 4 · 命令化让 UI 变复杂:每个 PATCH 都变成"打开命令面板 → 填原因 → 提交",Duke 一开始会觉得烦。
决策:本地模式(无认证)下,简化为"按钮 + 必填原因下拉框",1 步完成。命令面板作为高级入口。
问题 5 · 幂等键需要客户端管理:前端 JS 要生成 UUID,容易出错。
决策:前端用 `crypto.randomUUID()`,fallback 到 `Date.now() + Math.random()`。本地模式不强校验。
问题 6 · LTC 7 阶段在招投标可能过度:Duke 主要做 L3 投标,其他阶段是辅助。
决策:LTC 模型保留,但 UI 默认在 L3 投标,其他阶段折叠收起来,需要时展开。
问题 7 · ai_summary 算不算事实:v0.3 严格说"报告不能成为业务事实"。但 ai_summary 是 Mavis 写的语义总结,Duke 用来辅助决策。
决策:ai_summary 标记为 `summary_type="ai_reference"`,带 author + source,UI 显式标"📋 不是事实"。业务事实必须人工或命令确认。
