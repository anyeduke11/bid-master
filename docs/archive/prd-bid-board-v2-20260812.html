6.4 关键不变量(数据完整性)

约束说明
code 唯一客户代号全局唯一,建客户时校验
stage ∈ 6 枚举任何写入必须经过白名单,非法值拒绝
priority ∈ 3 枚举同上
ai_ready 数组去重同 key 不重复追加(避免噪声)
flow 节点为 source of truth客户当前进度的权威源是 bids.flow.nodes。stage / block / priority 三个字段均为派生字段。任何写入应直接改 flow 节点,再由系统反推其他字段,反之亦然。
stage 反推规则取 flow.nodes 中 status='progress' 的第一个节点 → 映射到 stage 枚举:
sales-bid→跟踪 / buy-rfp→审查 / quote→报价 / tech-solution|draft|final→修订 / seal→封标 / present→述标。
若所有节点 done → stage='封标';若所有节点 pending → stage='跟踪'。
block 派生规则取 flow.nodes 中 status='blocked' 的节点 → block 字段 = "[节点名] · [block_reason]"(逗号拼接所有阻塞节点)。
若无 blocked 节点 → block=''。
手动写 block 字段时,必须同时设置对应 flow 节点 status='blocked' 并填 block_reason。
priority 派生规则见 §6.5 优先级算法。自动算,但 Duke 可手动覆盖(覆盖后 priority_manual=true,自动重算跳过)。
due_at 与 flow.nodes[].plan_end改 due_at 时,按 §6.6 公式重算所有 plan_end。已被手动调整的节点(plan_end_manual=true)不被覆盖,保留 plan_end_auto 字段以备查。
code 唯一(重复声明)客户代号全局唯一,建客户时校验

6.5 P0 优先级算法

输入:bid.due_at、today、bid.flow.nodes。输出:bid.priority ∈ {P0, P1, P2}。

function calcPriority(bid, today = new Date()) {
  // 规则 1: 持续跟踪类(无截止)默认 P2
  if (!bid.due_at || bid.due_at === '持续') return 'P2';

  // 规则 2: 已封标(所有节点 done 且最后一个是 seal/present/notice/retro)→ 降为 P2
  if (bid.flow?.nodes?.every(n => n.status === 'done')) return 'P2';

  // 规则 3: 计算距截止天数
  const due = new Date(bid.due_at.replace(' ', 'T'));
  const daysToDue = Math.ceil((due - today) / (86400000));

  // 规则 4: 基础优先级(按天数)
  let priority;
  if (daysToDue <= 3)      priority = 'P0';
  else if (daysToDue <= 7) priority = 'P1';
  else                      priority = 'P2';

  // 规则 5: 阻塞升级(任一节点 blocked → 升一级)
  const hasBlock = bid.flow?.nodes?.some(n => n.status === 'blocked');
  if (hasBlock && priority === 'P1') priority = 'P0';
  else if (hasBlock && priority === 'P2') priority = 'P1';

  // 规则 6: 截止已过(天数 ≤ 0)且未完成 → 强制 P0(最紧急)
  if (daysToDue <= 0 && bid.flow?.nodes?.some(n => n.status !== 'done')) {
    priority = 'P0';
  }

  return priority;
}

// 执行时机:每日 09:45 bid-card-refresh cron 跑一次
// 手动覆盖:Duke 可在弹窗选 P0/P1/P2,设置 priority_manual=true

规则总览(便于查阅):

条件优先级说明
due_at = '持续' 或 nullP2持续跟踪类,默认 P2
所有 flow 节点 doneP2已完成,降为 P2(避免看板噪声)
T ≤ 3 天P0极度紧急
T ≤ 7 天P1本周内
T > 7 天P2下周及以后
任一节点 blocked原优先级 ↑ 1 级P2 → P1 → P0
T ≤ 0 天 且未完成P0已过截止,强制 P0(最紧急)
Duke 手动设置 priority_manual=true手动值覆盖自动计算

6.6 plan_end 自动反推公式

每个流程节点的 plan_end = bid.due_at - days_before_due 天。days_before_due 在流程模板(§6 数据模型)定义,负数 = 截止后 N 天(如讲标 D-1、公示 D+30、复盘 D+60)。

function calcPlanEnd(bid, nodeTemplate) {
  if (!bid.due_at || bid.due_at === '持续') return '';
  const due = new Date(bid.due_at.replace(' ', 'T'));
  due.setDate(due.getDate() - nodeTemplate.days_before_due);
  return due.toISOString().slice(0, 10);  // YYYY-MM-DD
}

// 例:due_at='2026-08-13 17:00',节点 'final' (days_before_due=3)
// → plan_end = 2026-08-10

12逻辑一致性审查审查
检查 PRD 各部分之间是否有矛盾、不一致、循环依赖。

⚠ 问题 12-1:block 字段语义双重身份

严重度:中 · 来源:数据模型 + 流程模型

在 bids 表中,block 是一个 string 字段(看板卡上显示);在 flow 节点中,block_reason 是阻塞原因。两者在 PRD 中没有明确同步规则。

  • 当 flow 节点 quote 被标记为 blocked,block_reason='报价签字' → 是否要写回 bids.block='报价签字'?
  • 反之,Duke 在看板手动写 bids.block='客户回复慢',是否要同步到 flow 节点的某个 status=blocked?
  • 如果两方向同步规则不一致,会出现"看板说阻塞在 A,流程图说阻塞在 B"的自相矛盾

建议:PRD 第 6.4 节"关键不变量"中已提到一致性,但没定义同步方向和优先级。需补充规则:flow 节点为 source of truth,看板 block 字段为派生。

⚠ 问题 12-2:stage 与 flow 节点位置 的双重表示

严重度:中 · 来源:数据模型 + API

客户的当前阶段用两个字段表示:

  • bids.stage:枚举(跟踪/审查/报价/修订/封标/述标)6 个值
  • bids.flow.nodes[i].status:每个节点的 done/progress/blocked 状态

这两者必须一致,但 PRD 没说谁是权威源。如果 bid.stage='修订',flow 中可能有 5 个 done + 2 个 progress,但哪个 progress 对应"修订"?

建议:flow 节点为权威,stage 由最近的 progress 节点反推(已在 demo 中实现 stageMap,但 PRD 没写)。

⚠ 问题 12-3:P0 / P1 / P2 优先级判定逻辑缺失

严重度:中

PRD 说"AI 自动算 priority",但没定义算法:

  • 什么条件从 P2 升 P1?
  • 什么条件从 P1 升 P0?(东莞 T-2 是怎么定的?)
  • P0 降 P1 的规则?

建议:P0 = T ≤ 3 天 OR 阻塞 + 客户核心;P1 = T ≤ 7 天;P2 = 其他。写在 PRD 6.4 不变量里。

⚠ 问题 12-4:"AI 就绪"与"阻塞"的边界模糊

严重度:低

ai_ready 是 AI 已完成的事项;human_todo 是人要做的;block 是阻塞原因。但"门禁:JSON/格式/公式 全过"是 AI 做的还是人做的?

当前 ai_ready 数组里有这种"门禁"项,但严格说门禁是流程环节不是 AI 输出。

建议:把"门禁"放到 flow 节点 seal 的 sub-status,而不是 ai_ready。或者 ai_ready 只放 AI 的"成果",不混流程节点。

⚠ 问题 12-5:截止日期 due_at 与流程节点 plan_end 一致性

严重度:中

PRD 6.4 提到"改 due_at 时自动重算 plan_end",但没说:

  • 重算触发是同步还是异步?
  • 如果 flow 节点已被 手动调整过(plan_end ≠ 自动算的值),重算是否覆盖?覆盖会丢数据。

建议:加 plan_end_manual 字段,只覆盖该字段,自动值仍保留在 plan_end_auto。展示用 manual,无 manual 用 auto。

✓ 通过项 12-6:数据流方向清晰

严重度:无

Skill → window.BidBoard → localStorage → BroadcastChannel → 其他 tab 渲染。数据流单向且无环,逻辑一致。

13批判性审查(找问题)审查
站在"为什么这个产品可能失败 / 没人用"的角度找问题。

🔴 假设错误风险:单用户场景是否真的够?

PRD 假设主要用户是 Duke 自己,但实际工作流中 Duke 经常把标书撰写交给同事。当同事也要看 swimlane 当前在哪一步,他们去哪里看?

可能后果:P1/P2 阶段多用户需求不解决,看板变成 Duke 的"个人玩具",团队价值衰减。

建议:P1 阶段加只读分享(生成只读链接),P2 加完整多用户。P0 不阻塞。

🔴 价值假设:"AI 跑完会推看板"是赌博

整个产品的核心价值是"Skill 跑完会调 BidBoard API"。但:

  • 已存在的 8 个 Skill 是过去 6-12 月写的,代码里没集成 BidBoard
  • 改造需要改 8 个 Skill 源码 → 回归测试 → 部署
  • 如果某个 Skill 跑完没调 API,看板永远停更(无信号 → Duke 误判)→ Duke 不信任看板 → 看板被弃用

建议:P0 第一周先做"卡死式强制"——如果 Skill 跑完没调 API,直接 block Skill 输出。要么改 Skill,要么用 webhook 兜底监听 Skill stdout。

🟡 噪音爆炸:107 源 × 看板 = 信息过载

看板当前 6 客户已够看,如果 107 源新闻事件都尝试写"action_items"到看板,会出现:每天 200+ 提示,90% 是噪声。

建议:看板只放人工/AI 已确认事项;新闻事件先经"漏斗"(L1 采集 → L2 去重 → L3 P0/P1)才进看板,不要直接把全部塞进去。

🟡 性能陷阱:swimlane 横向滚动 + 60 客户

PRD 说"支持 60 客户",但 swimlane 设计是"所有客户共享 13 列"。60 客户意味着 60 行 × 13 节点 = 780 个 DOM + 大量事件监听。在 4K 屏 / 大屏还行,MacBook 13 寸会很挤。

建议:

  • 10 客户以下:全显
  • 10-30 客户:分组折叠(按 P0/P1/P2 折叠非当前优先级)
  • 30+ 客户:虚拟滚动 + 默认折叠非 P0 客户

🟡 离线场景:飞机 / 断网怎么办?

Demo 用 localStorage 完全离线可用,但 PRD 7.1-7.3 的 HTTP API 需要联网。如果 Duke 在飞机上想看今天的看板,WebSocket / SSE 全部失效。

建议:localStorage 为权威源,API 仅用于远程同步;离线时所有操作入 localStorage,上线时 sync 队列冲掉(或冲突解决)。

🟡 移动端:PRD 说"P2 PWA",但没具体方案

投标常发生在客户现场、出租车上。手机上看 13 节点 swimlane 几乎不可读。

建议:移动端应该只看"今日动作 + 阻塞列表",不是完整 swimlane。PWA 也要拆 2 套布局。

🔵 边界案例:due_at='持续' 的客户(平安银行)

当前 due_at='持续' 时,flow 节点 plan_end 算不出(NaN date),swimlane 会显示"—"。但 PRD 没规定"持续"客户的优先级算法。是不是"持续"=P2?还是单独一类?

建议:加 bid.type='opportunity|tracking|active' 字段,active 走流程,opportunity 只看商机阶段。

🔵 时间戳混乱:last_sync 含义不清

PRD 5.4 说 last_sync = "最后同步时间",但没说是:

  • 任何字段变化的最后时间?
  • 还是只看 AI 写入?
  • 还是人工操作的最后时间?

Demo 当前是"任何 write 都更新",但 PRD 没明确。建议:last_sync = 最后任意写入(AI 或人),加 last_human_at / last_ai_at 拆开。
